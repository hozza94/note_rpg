# 구현 계획서 9: 아이템 풀 확장 + 대장장이 시스템 설계

## 1) 목표
- 아이템 다양성을 늘려 **파밍-교체-성장 루프**를 강화한다.
- 대장장이 기능을 추가해 아이템을 **강화/제작/분해**할 수 있게 한다.
- 기존 전투/드랍/상점 흐름과 충돌 없이 점진적으로 도입한다.

---

## 2) 현재 구조 요약
- 아이템은 `GAME_DATA.items` 단일 사전에서 관리 중.
- 장비는 `slot` + `stats` 중심(정적 수치), 재료는 설명형 아이템.
- 드랍은 `dropTables`, 상점은 `shops`로 지역별 고정 판매.
- 장비 효과는 `InventoryManager.getBonuses()`에서 합산 후 UI 반영.

### 현재 한계
- 장비 풀이 상대적으로 작아 교체 동기가 약함.
- 아이템 성장 수단(강화/제작)이 없어 드랍 반복 체감이 단조로움.
- 재료 소비처가 제한적이라 후반 재화 가치가 떨어질 수 있음.

---

## 3) 아이템 풀 확장 설계

## 3.1 확장 방향
- **세로 확장**: 지역/등급별 신규 장비 추가 (초중후반 계단형).
- **가로 확장**: 같은 슬롯에서도 성향이 다른 장비 추가.
  - 예: 공격형(ATK/SPD), 안정형(DEF/HP), 신앙형(FAITH/PP)
- **보스 고유 장비**: 보스 드랍에서만 획득 가능한 특화 아이템 추가.

## 3.2 데이터 설계(1차)
- 기존 `GAME_DATA.items` 구조 유지(호환 우선).
- 아래 필드만 선택적으로 추가:
  - `tags: string[]` (예: `['faith', 'tank', 'speed']`)
  - `uniqueEffect?: string` (설명 전용, 1차는 텍스트만)
  - `smithable?: boolean` (강화/분해 허용 여부)
  - `tier?: number` (1~5)

## 3.3 슬롯별 권장 추가량(초안)
- `weapon`: +10
- `armor`: +8
- `boots`: +6
- `helmet`: +6
- `accessory`: +8
- `offhand`: +6
- 총 **약 44개** 추가 (3지역 기준)

---

## 4) 대장장이 시스템 설계

## 4.1 기능 범위(1차)
1. **강화**: 장비의 기본 스탯을 단계적으로 상승
2. **분해**: 장비를 재료로 환원
3. **제작**: 레시피 기반 장비 제작

> 1차에서는 “옵션 랜덤 부여” 같은 복잡 기능은 제외하고, 고정 규칙으로 안정 도입.

## 4.2 핵심 규칙(초안)

### 강화
- 대상: `smithable !== false`인 장비
- 단계: `+0` ~ `+10`
- 비용: 골드 + 강화 재료(`giant_core` 계열/신규 재료)
- 성공률(예시):
  - `+0~+3`: 100%
  - `+4~+6`: 80% / 65% / 50%
  - `+7~+10`: 40% / 30% / 20% / 12%
- 실패 패널티(안):
  - `+0~+5`: 단계 유지
  - `+6~+10`: 1단계 하락
- 보정치 공식(간단형):
  - 각 스탯 `floor(baseStat * rate[level])`
  - `rate`: 0.00, 0.06, 0.12, 0.18 ... (스탯별 공통)

### 분해
- 장비 1개 -> 골드 일부 + 재료 1~3개
- 등급/강화 단계가 높을수록 환급량 증가

### 제작
- `recipes` 테이블 정의:
  - `resultItemId`, `costGold`, `ingredients[]`
- 지역별 제작 해금(보스 격파/탐험도 기준)으로 단계적 오픈

## 4.3 UI 진입/흐름
- `탐험` 하단 액션에 `🔨 대장간` 버튼 추가
- 모달 탭:
  - `강화`
  - `분해`
  - `제작`
- 강화 화면 핵심 정보:
  - 현재 단계, 다음 단계 예상 상승치, 성공률, 실패 패널티, 필요 재료
- 분해/제작은 즉시 결과 토스트 + 로그 기록

---

## 5) 데이터/저장 스키마 변경

## 5.1 상태값 추가(`state.player` 또는 별도)
- `smithLevel` (향후 확장용, 1차는 고정 1)
- `itemEnhance`: `{ [instanceId or itemId]: level }`

> 중요: 현재 인벤토리는 아이템 ID + 수량 구조라, “같은 아이템의 강화 단계 구분”이 어렵다.

## 5.2 인벤토리 구조 확장(권장)
- 현행: `{ id, count }`
- 목표: 인스턴스 장비 도입
  - 장비: `{ uid, id, enhance, locked }`
  - 재료: `{ id, count }` 유지

## 5.3 호환 마이그레이션
- 기존 세이브 로드 시:
  - 장비 아이템 수량을 개별 인스턴스로 펼침(`enhance=0`)
  - 재료는 기존 그대로 유지

---

## 6) 밸런싱 가이드(초안)
- 전투 TTK(평균 처치 턴 수)가 급감하지 않게 강화 상한 제어
- SPD 과도 상승 방지:
  - 강화로 SPD가 오르는 장비는 상승 계수 하향
- FAITH/PP 빌드도 끝까지 유효하도록 액세서리 라인 강화
- 보스 전용 장비는 강하지만 획득 난이도/재료 소모로 균형 유지

---

## 7) 구현 단계 제안

### Phase A (빠른 확장)
- 아이템 20~25개 먼저 추가
- 인벤토리/상점/드랍 표기 강화(비교 UI 포함)

### Phase B (대장간 MVP)
- 강화(+0~+5), 분해, 제작 일부 레시피
- (연기) 인벤토리 인스턴스화는 Task 5로 분리하여 후속 진행

### Phase C (고도화)
- 강화 +10, 제작 트리 확장, 보스 고유 제작식
- 보호 재료/보정형 재료(성공률 +n%) 도입

## 8) 리스크와 대응
- **리스크**: 인벤토리 구조 변경으로 기존 저장 호환 이슈
  - 대응: `ensureStateSchema()` + 일회성 마이그레이션 함수
- **리스크**: 강화 확률 스트레스
  - 대응: 저단계 확정 성공 + 실패 완충 재료 도입
- **리스크**: UI 복잡도 증가
  - 대응: 기본 정보만 우선 노출, 상세는 펼침/툴팁 처리
