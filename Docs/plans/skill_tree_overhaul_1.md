# 스킬트리 통합·확장 개편 계획 (1)

## 배경·현황

- **데이터 위치**: `js/data.js`의 `GAME_DATA.skillTrees.pilgrim` — `nodes`, `edges`, `clusters`, 노드별 `position`, `grants`(`stats` / `specials` / `activeSkillId`).
- **런타임**: `js/engine/skilltree.js` — 해금(`unlockSkillNode`), 패시브 합산(`getPassiveBonuses`), 액티브 동기화(`syncUnlockedActiveSkills`), 모달 UI.
- **세이브 보정**: `js/engine/state-schema.js` — 스킬 포인트를 `(레벨-1)*3` 기준으로 **부족분만** 보충.
- **액티브 과다**: 트리만 **14개** `active_unlock` 노드가 있고, 게임 시작 시 `meditation`, `praise`, `proclaim` 등 기본 액티브가 별재. 전투 UI·밸런스 관점에서 선택지가 과밀할 수 있음.
- **거리·효용 불일치**: 노드 `position`은 거미줄형 배치이나, **투자(거리) 대비 `grants` 강도**를 맞추는 공통 규칙이 없음.
- **저층 노드 밀도**: **시작점 근처 1~2칸**은 상대적으로 적고, 가지·서브클러스터가 중·후반에 몰린 구간이 많음.

## 1. 액티브 스킬 합성 (확정 설계)

**장착 슬롯·로드아웃 방식은 사용하지 않는다.**  
대신 **데이터 상으로** 여러 액티브를 **하나의 신규 스킬 ID**로 합성한다.

### 1.1 개념

- 예: 스킬 **A**, **B**를 합쳐 **C**를 만든다.
- **C의 전투 동작**: A에서 쓰이던 효과와 B에서 쓰이던 효과를 **한 번의 선택(한 턴·한 버튼)** 안에서 모두 수행하거나, 동일 시나리오를 커버하는 **단일 파이프라인**으로 구현한다 (기획에 따라 “순차 발동” vs “패키지로 한 방” 중 택일).
- **밸런스 원칙**: A만 쓸 때 + B만 쓸 때의 **합산 기대 효율**(딜·버프·생존 등)을 `1.0`으로 두면, **C 단독 사용의 기대 효율은 `α` (예: 0.82~0.92)** — 즉 “한 슬롯에 묶인 대가”로 **명시적으로 약화**.
  - `α`는 스킬 등급·PP 비용·쿨다운 유무에 따라 구간을 둘 수 있음.

### 1.2 데이터 스키마 (안)

`GAME_DATA.skills`에 합성 메타를 둔다 (이름은 예시).

```text
merged_from: ['smite', 'holy_wall']   // 참고용 / 툴팁 / 감사
merge_profile: {
  damageMul: 0.88,                   // A+B 단독 대비 딜 배율
  secondaryEffectMul: 0.85,          // 보조 효과(쉴드·디버프 등) 배율
  ppCostRule: 'sum_then_discount'    // 예: PP 합의 90% 등, 별도 테이블화
}
```

- **트리 노드**: 기존 `pilgrim_active_smite` 등을 **한 노드** `pilgrim_active_xxx`로 줄이고 `grants.activeSkillId: 'merged_smite_wall'`처럼 **C만** 해금하도록 변경.
- **구 A·B 전용 노드**는 제거하거나, **C 해금 전제**가 되는 패시브 노드로 흡수.

### 1.3 구현 범위

- **`battle.js`(및 관련)**: C 스킬 분기 추가 — 내부에서 기존 A·B 로직을 **함수 단위로 재사용**하되, 위 배율·PP를 적용.
- **`skills` 텍스트·아이콘**: C 전용 이름·설명 (A+B 구성 요약 문구).
- **`syncUnlockedActiveSkills`**: 해금 노드가 줄어든 만큼 `activeSkillIds`에 들어가는 ID 개수 감소.
- **세이브 호환** (`state-schema`):  
  - 구 `activeSkillIds`에만 있던 A·B 제거 후 C 추가, 또는  
  - 이미 A·B 노드를 찍은 세이브는 **C로 간주**하는 매핑 테이블 유지.

### 1.4 기획 산출물 (필수)

- **합성 매트릭스 표**: (A, B) → C, `α`·PP 규칙·우선순위(어떤 쌍부터 합칠지).  
- **전투 UX**: 합성 후에도 버튼 수가 줄어드는지, 롱프레스 등 추가 조작이 필요 없는지.

## 2. 거미줄 레이아웃에 맞는 “거리·투자” 지표 (제안)

레이아웃은 **중앙 시작점**에서 **방사형 주축(다리)**이 뻗고, 노드 간 **가로 연결(거미줄)**이 얽는 형태다.  
순수 유클리드 거리만 쓰면 “같은 다리 위 한 칸”과 “옆 다리로 횡단 한 칸”이 **같은 r**로 찍힐 수 있어, **밸런스와 어긋날 수 있다.**

### 2.1 1순위: **중심까지 최단 경로 길이 `L`** (엣지 수)

- 그래프를 무방향으로 보고 `pilgrim_origin`에서 BFS로 각 노드까지 **최단 엣지 수** `L`을 계산한다.
- 의미: 플레이어가 실제로 **스킬 포인트를 몇 번 써서** 그 노드에 닿는지와 가장 잘 맞고, **거미줄 가로 연결**도 “한 걸음”으로 자연스럽게 반영된다.
- **효용 감사의 기본축**: 같은 `kind`(예: `small`)끼리 **`L`이 클수록** 환산 효용 점수가 **단조 증가**하도록 구간 규칙을 둔다.

### 2.2 2순위: **방사 좌표 `r` + 주축 각도 θ** (시각·클러스터 정렬)

- `position`의 `r = sqrt(x² + y²)`, `θ = atan2(y, x)` (또는 데이터에 `spokeId`를 명시).
- 용도:  
  - 같은 `L` 안에서 **바깥 그림이 더 멀어 보이게** 배치했는지 점검.  
  - **클러스터별 밀도**(한 방향 다리에 소노드가 너무 적은 구간) 시각화.
- **밸런스 1차 규칙에는 `L`만 필수**로 두고, `r`은 보조 지표로 둔다.

### 2.3 3순위(선택): **주축 투영 깊이 `S`**

- 메인 3~4 다리(신앙·전투·수호·기동 등) 각각에 “다리 위 순서 번호”를 부여할 수 있으면, 크로스링크 노드에 **`S` + 횡단 패널티** 같은 하이브리드도 가능하다.  
- 초기에는 **BFS `L`만으로 감사 스크립트**를 돌리고, 이후 트리가 복잡해지면 `spokeId`를 데이터에 넣는 방향을 권장.

### 2.4 효용·액티브

- 패시브: 기존처럼 **등가 점수** 환산 후 `L` 구간별 상·하한.  
- 액티브(합성 C 포함): **단독 A+B 대비 C의 `α`**, PP, 기대 DPS를 한 줄로 표시해 **합성 스킬이 “멀리 있는 노드일수록” 더 관대한 `α`를 가져도 되는지**는 별도 정책(보통은 **노드 위치보다 합성 티어**로 조절).

### 2.5 프로세스

1. 스크립트: 각 노드에 `L`, `r`, `kind`, 환산 점수 출력.  
2. 이상치: `L`이 큰데 패시브 점수가 낮음 / `L`이 작은데 과도함.  
3. 규칙 문서화 후 `grants`·엣지·위치 수정.

## 3. 저층 노드 확대 + 핵심·특성 코어 개편

### 3.1 레이아웃 원칙 (거미줄과 정합)

- **중심 링**: `pilgrim_origin` 직결 1엣지 구간에 `small` **다수** — “다리를 타고 첫 발을 내딛는” 구간 밀도 확보.  
- **다리 중간**: `notable`·약한 `specials`로 빌드 취향 분기.  
- **다리 끝·거미줄 교차**: `keystone`, **합성 액티브 해금**, 대형 보상.  
- **특성 코어**: 작은 거미줄 구름 안의 중심 1노드(강한 단일 보너스) — `kind` 확장 검토.

### 3.2 그래프 작업 순서

1. 주축·교차점 동선 스케치 후 `edges` 확정.  
2. 신규 노드 ID 발급(재사용 금지). 삭제 노드는 세이브 마이그레이션.  
3. `clusters`·모달 줌/필터 필요 시 UI 작업.

### 3.3 세이브·호환

- 삭제·병합 노드: **스킬 포인트 환급** 또는 **대응 노드 매핑**.  
- 액티브 합성과 **동일 패치**에서 `activeSkillIds`·해금 노드 정리를 한 번에 처리.

| 단계 | 내용 | 의존 |
|------|------|------|
| P0 | 합성 매트릭스(A,B→C), `α`·PP 규칙, 전투 동작(순차/패키지) 확정 | — |
| P1 | BFS `L`·`r` 노드 감사 스크립트 + 효용 표 | P0와 병행 가능 |
| P2 | 신규 `skills` 합성 항목 + `battle.js` 처리 + 트리 `active_unlock` 정리 + 세이브 마이그레이션 | P0 |
| P3 | 저층 소노드·코어·거미줄 재배치 데이터 작업 | P1·P2 반영 후 |
| P4 | 회귀 테스트(전투·로그·툴팁) | P3 |

## 리스크·주의

- 합성 C는 **구현 복잡도**가 높음 — A·B 효과를 **진짜로 모두** 넣을지, 일부는 “약화된 단일 효과로 요약”할지 P0에서 범위를 못 박기.  
- `skills`·`battle.js`·몬스터 스킬 참조 **전수 검색** 후 구 ID 제거.  
- 노드 수·합성 수에 맞춰 **스킬 포인트 경제** 재검토 가능.

---

## 확정 요약 (사용자 결정 반영)

1. **합성 스킬 C**: A·B 기능 포함, 단독 사용 대비 **의도적 약화 배율** 적용. 장착 개념 없음.  
2. 본 문서 전체를 위 1번 기준으로 재설계함.  
3. **거리 지표**: 거미줄 구조에 맞게 **1순위 = 시작점 BFS 최단 엣지 수 `L`**, **2순위 = 방사 `r`(및 선택적 θ / 주축)** 로 감사·밸런스한다.

## 설계 방향 보정 (직업 vs 핵심 코어)

- 플레이어 성장 분기는 **별도 “직업” 선택이 아니라**, 한 트리 안의 **핵심(keystone)·특성(notable)·클러스터** 조합으로 표현한다.  
- `classId`는 세이브·코드 호환용으로 `pilgrim` 단일 트리에 고정하고, UI에서 직업 전환을 두지 않는다.

세부 수치(`α` 기본값, PP 합성 규칙)만 추후 수치 테이블로 고정하면 P2 구현에 착수할 수 있다.
